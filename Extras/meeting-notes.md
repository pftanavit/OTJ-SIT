## Combining Clusters, ArgoCD, and GitOps


### Overview

1. From Proxmox that is currently managing the server, use Terraform to build and create 3 new VMs. `terraform apply` or test with `terraform plan`.

2. Then, with Ansible install RKE2 to configure the 3 nodes together to form a cluster. Once it becomes a cluster, the VMs now becomes a kubernetes nodes and assign this new cluster to Rancher.

3. Create a new repo that contains the desired state of the cluster. 

4. With Argo CD, install it into the cluster and points it towards the repo. Bridge between git, and cluster.

## Detailed Steps

**1. Compute Provisioning.** Transform empty server resources into functioning networked virtual machine.

- `Code`: Write declarative `.tf` configuration using a Proxmox Terraform provider. Define VM specs such as CPU cores, memory, disk size, network bridge, and optionally cloud-init settings (hostname, SSH keys, IP configuration).

- `Dry Run`: Run `terraform plan` to compare desired state with current Proxmox state. It generates an execution plan showing what will be created, changed, or destroyed.

- `Execution`: Run `terraform apply`. Terraform calls the Proxmox API to create the three VMs from a base template and configure them according to the Terraform configuration.

- `Cloud-Init Injection`: During the clone process, Terraform passes "Cloud-Init" data to the new VMs. This sets their static IP addresses, hostnames, and injects the SSH keys so you can log in without password.

- `Output`: Terraform completes and outputs the 3 new IP addresses.

**2. Orchestration**. Turns 3 isolated virtual machines into a unified and managed cluster.

- `OS Hardening`: Ansible SSHes into the 3 new IPs. Disables swap memory, configures Linux kernel parameters (sysctl) required by Kubernetes networking, and adjusts firewall to prepare for Kubernetes.

- `RKE2 Bootstrap`: Ansible installs the RKE2 binary on the first VM and starts it with the CNI configuration set to `none`. The first VM becomes the initial Kubernetes control-plane node, standy by for an external network plugin.

- `Joining Cluster`: Ansible takes a secure token generated by the first node and uses it to install `RKE2` on the remaining 2 VMs. These VMs use the token to securely attach themselves to the first node completing a cluster.

- `CNI Installation`: Ansible applies Cilium directly (via `helm install` or `kubectl apply`) against the new cluster's kubeconfig. Nodes transition to Ready and pod networking becomes functional.

- `Rancher Assignment`: Ansible runs `kubectl apply` command that install `Rancher` agent. This agent connects to the main `Rancher management server` registering it so that it appears on the Rancher dashboard. This imports the cluster into the existing Rancher server.

**3. Git Repository**. Before automating application deployments, we need to define the application and its infrastructure.

- `Desired State`: Create a Git repository that is structured with all the requirements and directories.

- `Declarative Manifests`: Complete the folder with Kubernetes YAML files or Helm chart. For example, including Cilium as the network layer.

**4. Automation Bridge**. With GitOps, link the cluster to the Git repository.

- `Argo CD`: With command `kubectl apply`, install the Argo CD directly into the new `RKE2` cluster.

- `Connection`: Provide Argo CD with the URL to the Git Repository to tell it where to look at.

- `Reconciliation Loop`: Argo CD compares the Desired State from the Git repo against the Actual State that is running in the cluster.

- `CD`: With Continuous Delivery, Argo CD continuously watches the Git repository for changes and builds the resources inside the cluster. If a new commit is pushed, Argo CD automatically updates the cluster to match.
